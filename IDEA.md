# GitCraft: Minecraft GitOps

## Идея

GitCraft — устанавливаемая система управления Minecraft-сервером через GitHub. Git хранит желаемое состояние сервера, а агент на машине применяет одобренные изменения, когда на сервере нет игроков. Настройки полностью отделены от бинарных файлов и игровых данных.

Есть два вида репозиториев:

- Репозиторий инструмента: агент деплоя, бот обновлений, установщик, Web UI, шаблоны и документация.
- Репозиторий конкретного сервера: конфиги Minecraft и плагинов, указатели на ядро/плагины/моды, ограничения совместимости и GitHub Actions.

Миры, данные игроков и плагинов, `.jar`, резервные копии, логи, токены и пароли в Git не попадают.

## Работа команды

Разработчик меняет настройки в своей ветке и открывает Pull Request в `main`. CI проверяет синтаксис и структуру конфигурации и указателей. Ответственные разработчики одобряют PR. Правила защиты ветки обеспечивают обязательность проверок и одобрений; CODEOWNERS назначает ответственных. После слияния агент обнаруживает новый коммит.

## Два независимых агента

Бот обновлений запускается по расписанию в GitHub Actions. Он проверяет источники релизов, выбирает стабильные версии в заданных пределах совместимости, обновляет точные версии, URL и SHA-256 и открывает PR с описанием изменений. Источник поиска и закрепленная версия — отдельные поля. Новая версия не устанавливается до прохождения обычного процесса одобрения. Мажорные переходы Minecraft и смена загрузчика требуют отдельного решения.

Агент деплоя работает на сервере и устанавливает только состояние конкретного одобренного коммита `main`. Ему достаточно доступа к репозиторию на чтение. У сервера нет необходимости пушить журналы в репозиторий.

## Безопасный цикл деплоя

1. Захватить блокировку от параллельных запусков и получить состояние Git.
2. Сравнить целевой коммит с последним успешно установленным.
3. Подготовить отдельный staging-каталог: выгрузить конкретный коммит, проверить настройки, скачать нужные файлы и проверить SHA-256. Совпадающие файлы можно брать из проверенного кеша.
4. Проверить онлайн через RCON. Игроки есть — отложить. Недоступность RCON или непонятный ответ — тоже отложить, а не считать сервер пустым.
5. Дождаться заданного периода пустого сервера и повторить проверку непосредственно перед остановкой. Гонка входа игрока между проверкой и остановкой должна учитываться; абсолютная гарантия требует блокирования новых подключений на переходе.
6. Корректно сохранить мир и остановить Minecraft через systemd.
7. Создать резервную копию изменяемых управляемых файлов, применить настройки и бинарники, включая удаление только ранее управляемых файлов, которых больше нет в манифесте. Не удалять рабочие данные плагинов и миров.
8. Запустить сервер и проверить готовность через RCON, а не только наличие процесса.
9. При успехе записать установленный коммит и журнал операции. При ошибке вернуть предыдущие управляемые файлы и попытаться запустить предыдущую версию, явно записав результат.

Несовпадение хеша скачанного файла прерывает обновление. Откат бинарников и конфигов не отменяет миграции мира или базы плагина: перед потенциально несовместимыми обновлениями нужны копии соответствующих данных и отдельная политика допуска. Автоматический откат мира может потерять изменения игроков и не выполняется молча.

## Установка

Первичная поддержка — Debian и Ubuntu с systemd. Установщик определяет ОС, проверяет поддержку, устанавливает зависимости, подготавливает отдельного пользователя Minecraft, каталоги и сервисы. Java устанавливается или выбирается явно; версия запуска закрепляется абсолютным путем к исполняемому файлу. Поддержка SDKMAN может быть добавлена как отдельный способ управления Java.

Установщик запрашивает репозиторий, настройки Minecraft, способ авторизации GitHub и параметры Web UI. Он умеет подготовить новый конфигурационный репозиторий из шаблона или предложить изменения существующего через ветку и PR. Для этого первоначальная настройка может потребовать более широких GitHub-прав, которые не нужны агенту во время обычной работы. Токены не записываются в Git и не выводятся в журналы.

Установка повторно запускаема: существующие настройки и игровые данные сохраняются. Сетевые настройки применяются явно с сохранением доступа администратора; RCON не публикуется в Интернет.

## Конфигурация и Web UI

Все параметры доступны в обычных текстовых файлах. Web UI — легкая оболочка над этими файлами, а не обязательный компонент агента.

Локальные настройки: `/etc/gitcraft/agent.yml`, `/etc/gitcraft/web.yml`; секреты: отдельный файл окружения с ограниченными правами. Общие правила сборки, конфиги Minecraft и указатели зависимостей находятся в конфигурационном репозитории.

UI показывает состояние Minecraft, онлайн, установленный и ожидающий коммиты, версии компонентов, причины ожидания и историю операций. Он позволяет проверять изменения, запрашивать безопасное применение и откат, редактировать локальные настройки с валидацией. Изменения репозиторных настроек должны проходить через PR. Секреты не возвращаются браузеру открытым текстом. По умолчанию UI слушает loopback; внешний доступ требует аутентификации и защищенного транспорта.

## Файлы на машине

```text
/opt/gitcraft/                  # Установленный инструмент
/etc/gitcraft/                  # Локальные настройки и секреты
/var/lib/gitcraft/repository/   # Локальная копия конфигурационного Git
/var/lib/gitcraft/staging/      # Подготовленные обновления
/var/lib/gitcraft/cache/        # Проверенные jar
/var/lib/gitcraft/state/        # Установленный коммит и состояние операций
/var/lib/minecraft/server/      # Рабочий Minecraft, миры и данные
/var/backups/gitcraft/          # Резервные копии
```

## Первый рабочий этап

Единый бинарник на Rust с CLI, валидируемыми YAML/JSON-конфигами, реальным RCON, fetch конкретного коммита, staging и проверкой хешей, управляемым копированием, systemd, журналом и восстановлением. Бот обновлений с ограниченным набором явно поддерживаемых источников, шаблон репозитория, установщик с безопасным режимом подготовки и легкий Web UI. Проверки выполняются на временных каталогах и подменных сервисах без изменения текущей машины.

Далее: расширение источников и загрузчиков модов, управление PR из UI, улучшенное резервное копирование, уведомления и дополнительные дистрибутивы. Поддержка каждой возможности должна быть явно указана; неподдерживаемые источники и действия завершаются понятной ошибкой.

## Организация разработки

Оркестратор принимает архитектурные решения и координирует работу. Исследования, реализация, локальное устранение проблем и проверка делегируются субагентам. Решения, которые меняют согласованную идею или требуют пользовательских данных, обсуждаются с владельцем проекта.
